# Release promotion and rollback tracking

No step here has been executed against production. Keep current mixed-worktree inventory as historical evidence and create a distinct future release record. A new app/web pair must come from one approved full application SHA. Preserve the existing separate app/web identities until a tested migration is explicitly approved.

1. Select a reviewed application commit; verify pinned submodule and all required backend/frontend/SECA jobs, including production V2 crash recovery where used. Record CI run ID, full SHA, SECA SHA, lockfile hashes and build platform. A successful default-branch run is insufficient unless its SHA matches the candidate.
2. Build paired app/web artifacts after tests, scan dependencies and images, and produce SBOM/provenance. Independently approve publication after confirming package privacy. Capture actual immutable registry digest references and retain prior releases against cleanup. Never derive a registry digest from a local image ID or tag spelling.
3. Retrieve both digests with development-only read credentials. Use a fresh Compose project, loopback ports, synthetic SQLite/SECA/RAG fixtures and nonproduction mounts. Disable paid external API calls and scheduling or point it at an isolated synthetic service. Test app/web endpoints, scheduler behaviour in isolation, SECA persistence/replay and schema compatibility; record retrieved local config IDs and exact platform. No production secrets, databases or Caddy volumes are used for this validation.
4. Prepare a reviewed infrastructure manifest change. Preserve `schema_version: 1` and historical observations. Per image, `provenance.source_revision` is the full approved SHA, `platform` is observed, and `registry` contains the actual `reference`, `digest`, `platform`, matching `source_revision`, and `verification: retrieved-and-tested` only after successful retrieval and testing. App/scheduler records must be identical. Caddy needs its own upstream digest and retrieval evidence; its application source revision may be null. Archive recovery evidence is recorded separately using the image workstream contract. Keep CI run, build/scan/attestation evidence and development results linked in an operator ledger; do not fabricate evidence fields.
5. Resolve deployment configuration according to `docs/deployment/` and run offline image validation, strict recoverability validation, then release preflight against the candidate and target settings. Resolve every missing environment path, pinned config hash, mount, port, project identity and compatibility blocker. Review the human-readable plan. A manifest update or green preflight does not authorise deployment.
6. Identify an already retrieved, tested previous release. Confirm its digests/archives remain retrievable, its source/config remains available, its secrets are in protected storage, and a backup has passed restore validation for the required point in time. Review forward/backward database and SECA state compatibility. An image rollback cannot undo an incompatible state migration.
7. Request explicit production approval for the exact candidate, preflight plan, maintenance implications and rollback release. This task installs no production deployment workflow. A later operator-driven deployment must verify immutable artifacts and back up state as approved before changing services.
8. After any future authorised deployment, record release ID, manifest Git commit/hash, app/web/Caddy references, platforms, operator approval, deployment time, preflight result, backup/restore validation ID, previous release ID and health results. If verification fails, stop promotion and apply only the separately approved rollback procedure.

The release ledger is an operator-managed record outside runtime data and must exclude environment values, credentials and production inspect output. Git can hold nonsecret release metadata and evidence references after review; backups, image archives and detailed runtime evidence stay in protected storage. Preserve a prior release rather than mutating its digest fields in place. Production rollback must select that exact verified release and rerun the same preflight, with explicit approval for any state restoration or container recreation.

Current blockers: exact legacy images have no verified registry/archive recovery evidence; Docker metadata inspection is denied; production restore validation has not been authorised; creation-time environments and Caddy active config remain unknown; source preservation and public repository/privacy decisions remain operator tasks. Synthetic tests and a workflow proposal cannot close those operational gaps.
